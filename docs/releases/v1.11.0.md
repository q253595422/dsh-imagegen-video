# v1.11.0 · 画布跑整条链路，而不是一个节点

> 各版本改动见 [CHANGELOG.md](../../CHANGELOG.md)。

这一版之前，画布只能「选中一个节点、点一次生成」。一条三段的链路要点三次，
中间还要等前一段出结果才能点下一段；其中任何一次忘了点，下游就永远等着。

1.11 把这件事交给执行器：**给一个起点，剩下的按依赖顺序自己跑完**。

> **这一版的 Release 是事后补发的。** 当时打包校验在「缺发布说明」处中止了整次
> 任务，tag、GitHub Release 与 npm 都没有产生；功能本身随后随 v1.13.0 到达用户
> （1.12.0 与 v1.13.0 在同一次推送里，Release 只按推送末端发了一次）。
>
> 下面的归档**不是当初那次 CI 构建的产物**（那次根本没跑成）。它是在补发时从本版
> 的提交 `3f7df02` 的树上重新构建、打包并由 `verify-pack.mjs` 校验过的，`SHA256SUMS`
> 对应这一份字节。安装行为与当时的代码一致，但它没有经过那一次发布流水线的验证。

## 从哪开始，往下跑多少

- **起点是选中节点。** 画布底部的「运行工作流」从当前选区往下走，只跑它的下游
  闭包——旁边的分支不动。
- **没选中时补完这块画布。** 起点取「还没有产出、或上次失败」的图片与视频节点，
  等于「把该跑的补完」。全部都有结果时不提交任何东西，而是提示「选中要重跑的
  起点再运行」，而不是假装跑了一轮。
- **已经有结果的节点直接复用。** 重跑一条链路不会为已经产出的节点再付一次费用。

## 顺序由依赖决定

分层的规则是纯函数（`src/client/workflow-graph.ts`）：同一层里的节点互不依赖，
一起提交；下一层要等上一层的结论。链越宽跑得越快，链越长也不会出现「下游先跑、
拿到空输入」这种假失败。

**环在提交前就被拒绝。** 自环也算环——一个节点连到自己，意味着它要等自己的产物。
检测到环时**一个节点都不提交**：跑一半再报错，用户要自己判断哪些结果是这次生成的。

## 失败只停它自己的下游

这条是刻意与「一错全停」不同的。一个节点失败，它下游拿不到输入，继续跑只会产生
一串看起来像系统坏了的错误，所以那些节点**不提交**；但图上与它无依赖关系的分支
照常跑完。

结果因此有三种，而不是「成功 / 失败」两种：

| 状态 | 含义 |
| --- | --- |
| `completed` | 全部有结论（含复用与跳过） |
| `partial` | 有节点失败，但至少有一条独立分支真的产出了结果 |
| `failed` | 有节点失败，且没有任何独立分支产出 |

「跳过」不算产出：提示词、配置这类不发起调用的节点算有结论，但不能拿来证明
「这次跑出了东西」。

## 进度与中止

运行卡片报告当前层与已完成节点数。**中止在层与层之间生效**——已经提交出去的
生成任务会继续跑完（那是收不回的），只是不再提交新的一层。

## 检查

- 排程规则（`planLayers` / `planWorkflow` / `downstreamClosure`）是纯函数，
  `scripts/smoke-workflow.mjs` 离线覆盖分层、环、空计划与重复连线。
- 执行器（`src/client/workflow-runner.ts`）不依赖引擎：它只负责顺序，生成仍然
  走画布原有的「提交 → 轮询回填」链路，所以不会出现第二套并发与重试逻辑。
- `pnpm test:workflow` 可单独跑，不需要网络。

## 已知边界

- **不设并发上限。** 真正的上限在生成队列（视频是 1），执行器不再加一层限流。
  层很宽时，任务会一起排进队列，按队列的规矩一个一个走。
- **只有「往下」。** 这一版只跑下游闭包，不支持从叶子往回补算上游。
