# v1.33.1 — 视频历史里那条删不掉的「3D 导演台导出」

> 用户报的是四个字：「删不掉？」——历史侧栏里有三条一模一样的「1:1 · 64x64 · 0.2s · ffmpeg」，蓝方块缩略图，点垃圾桶没反应。
>
> 查下去发现是两件事叠在一起：**那三条根本不是生成结果，是测试产物**；而它们之所以删不掉，是因为同一个 id 被写了三遍，前端撞 key、删除侧又只清了一半。这一版把两个根因都修掉，也把那道本该拦住它们的守门补上。

## 那三条是什么

`scripts/smoke-stage-encode.mjs` 的 E9 用例真的调 `stageEncodeSession()`——不是打桩，是走完整条编码路径。它在编码成功后会把成片写进视频库，这本身是对的：测的就是「导出的 mp4 能被宿主编出来」。

问题是这个脚本**没有隔离数据目录**。它 `import` 了 `mkdtempSync` / `rmSync`，却一次也没有调用；`DSH_HOME` 于是解析成 `~/.dsh/dsh-imagegen`，也就是用户的真实库。每跑一次 `pnpm test`，就往里追加一条测试片：

| 字段 | 值 | 来源 |
|---|---|---|
| 缩略图 | 64×64 纯蓝 | `makePng(64, [40, 90, 160])` |
| 时长 | 0.2s | 6 帧 / 30fps |
| model | `ffmpeg` | 走宿主编码 |
| prompt | 「3D 导演台导出」 | 写死在脚本里 |
| id | `stage-e9-real` | 会话 id 固定为 `e9-real` |

三个字段凑在一起，界面上就是一行看起来完全正常的记录——除了它永远不消失。

## 为什么删不掉

两处叠加，单独任何一处都不至于。

**存储层：同 id 只覆盖一半。** `appendVideoHistory` 走的是追加。索引里于是堆着三条 id 完全相同的记录，而列表拿 `video:${id}` 当 React key——三行撞在同一个 key 上，React 把它们当成同一行反复复用，渲染出来的「三条」其实是同一份数据的三次复用。

**删除层：抹索引和删文件不是同一个集合。** `removeVideoHistory` 用 `filter(id !== x)` 一次性抹掉全部同 id 条目（这一点是对的，旧索引里的重复必须靠它清干净），但紧接着只 `find` 第一条的文件去 unlink。结果是索引里三条全没了、磁盘上留两个孤儿 mp4；而前端因为 key 撞车＋重新读回来的那份还没落盘，用户看到的是「点了删除，行还在」。

同一条链上的 `appendHistory` / `removeHistory`（图片历史）是同一个形状，只是还没被踩到。

## 修了什么

1. **脚本隔离数据目录。** `smoke-stage-encode.mjs` 在最前面把 `DSH_HOME` 指到 `mkdtempSync(...)`，收尾 `rmSync` 删掉。跑一遍 `pnpm test` 不再碰真实库。
2. **写入按 id 覆盖，不再追加。** `appendVideoHistory` 与 `appendHistory` 都改成「先删同 id 的旧条目（连同文件），再放到最前」。`id` 本来就是调用方给的稳定标识——导演台按会话 id、拼接按 compose id——重写指的是同一条结果被重新保存。代价写在注释里：被覆盖那条独有的 poster 会一起删掉，这是正确的，否则就是永久孤儿。
3. **删除清掉同 id 的全部文件。** `removeVideoHistory` / `removeHistory` 的 `find` 改成 `filter`，每条同 id 条目的文件都 unlink。这条专门对付**已经写在盘上的旧索引**——去重只管新写入，用户机器上那三条还得靠它清干净。
4. **前端兜底去重。** `unifiedHistory` 与 `groupHistoryEntries` 按 id 收口（`new Map(...).values()` / `seen` Set）。存储层修好之后，盘上仍可能有旧重复条目，而列表是只读投影，在这里再挡一层没有副作用。
5. **守门扩到视频库、图片历史与画廊。** 这才是它一直绿着的原因：`verify-test-isolation.mjs` 的 `WRITE_MARKERS` 只认画布写入（`canvas/create`、`canvasStore.*`），所以 `smoke-stage-encode` 每跑一次都在写用户的库，而检查从头到尾没看它一眼。现在 `appendVideoHistory` / `stageEncodeSession` / `appendHistory` / `appendGallery` 都算写盘动作，提示文案也从「会写画布」改成「会写用户数据」。

## 验证

新增两条断言进 `smoke-history-canvas.mjs`，都是这个 bug 的直接反面：

- **「同一个 id 再保存一次是覆盖」**——连写三次同 id，`listVideoHistory` 必须只剩一条，且是最后那次的内容。
- **「删除一个 id 会连它名下所有旧文件一起清掉」**——直接造出「去重之前」的三条同 id 索引、各自指向不同文件，`removeVideoHistory` 之后三个 mp4 都必须不在磁盘上。

两条都做过反向注入：把 `appendVideoHistory` 去重改回追加 → 第一条立刻红（`3 !== 1`）；删掉 `smoke-stage-encode.mjs` 的隔离 → 守门立刻报出这个文件名。恢复后全绿。

`pnpm run typecheck`、`pnpm test` 全量、`verify-test-isolation.mjs`（80 个脚本 / 7 个写盘者全部指向临时根）通过。

## 你机器上那三条

已经不在盘上了：`~/.dsh/dsh-imagegen/videos/index.json` 只剩 8 条真实记录，`files/` 下 0 个 `stage-*`，mtime 停在这一轮排查之前。界面上如果还留着行，是宿主进程里的旧渲染状态——重启 App 即可，不需要再点一次删除。

装了这个版本之后，`pnpm test` 也不会再往真实库里写测试片了。

## 已知边界

- **旧索引里的孤儿文件只能靠「删那一条」清掉**，没有一次性扫描。刻意不做：扫描要在每次启动时遍历整个 `files/` 并判断哪些没人引用，而「没人引用」的判定一旦写错就是删用户的数据。宁可让孤儿多待一会儿，等用户删到它。
- **`id` 相同即视为同一条**。如果将来有调用方需要「同一份内容保存两次、两条都在」，得换一种 id 生成方式，而不是把这个覆盖改回追加。
