# v1.16.1 — 历史详情补全、两块结果板互斥、发布产物真正可重现

一句话概括：修掉 1.16.0 的三个缺陷——历史记录不显示生成参数、点不同历史会同时出现两块结果板、发布产物换个目录构建就变字节；另外把「结果板换成别的样子」收口成编译期就能拦住的形式。

## 为什么

**第一类：数据一直在，只是没人渲染。** 宿主从生成那一刻起就把 `prompt`、`size`、`quality`、`detail` 一并写进历史索引，`historyList` 也一直原样返回。前端从 1.16.0 起只渲染「本次生成 N 张」和时间，于是用户点开一条历史，看不到这条是怎么生成的。补渲染时还有个容易踩的坑：参数必须取自**这条历史记录**，不能取表单里「下次要生成」的值——否则界面上永远是「当前设置」，而不是「这条记录的设置」。

**第二类：两块结果板的条件互不排斥。** 视频板判 `resultSurface.kind === 'video'`，图片格判 `images.length > 0`。一次生成完成会 `setImages(...)`，但如果此刻结果板正开着一条视频历史，图片格就会重新长出来贴在视频下面。1.16.0 的第一次修法是「两个板面各加一个条件」——那正是缺陷的成因：互斥靠两处条件恰好互补，任何一处被改、任何新的写入路径都会让它复活。

**第三类：检查本身抓不到它该抓的东西。** `verify-reproducible.mjs` 原先只在**同一目录**构建两次再比字节，所以「绝对路径进了 CSS Module 类名哈希」这种路径依赖永远不会被它看见。另外 `tsconfig.json` 不在构建输入清单里——它是 tsdown 之外的另一条静默输入通道（rolldown 自己读它），改一条 `target` 就能让产物变字节，而检查当时不会抱怨。

## 做了什么

- **历史详情渲染。** 图片板与素材库的 `canvasMeta` 统一取自 `viewingImageEntry`（这条历史自己的 `prompt` / `size` / `quality` / `detail`），数量用 `images.length` 而不是历史条目里的 `n`——两者在「一张图生成失败」这类情况下会分叉。视频板补 `prompt` 与 `resolution`。i18n 全部复用现成 key，没有新造。
- **结果板单一派生。** 新增 `resultSurfaceOf(boardView, viewingVideoEntry)`（`src/client/ImageGenPanel.tsx:2689`）产出四个状态：图片历史、视频历史、素材库、什么都没选。两个板面都只读这一个值，`switch` 穷尽分支加 `assertNever` 兜底：以后加第五种状态，编译期就报错，不会出现「新状态只被一个板面认识」。
- **发布产物可重现。** `tsdown.config.ts` 交给 lightningcss 的 CSS Module 标识从绝对路径改为仓库相对路径（`cssRepoPath()`，`tsdown.config.ts:60-66`）。`scripts/verify-reproducible.mjs` 改为在**另一个目录**再构建一次，逐字节比对 `lib/` 下**全部 5 个产物**（此前漏了 `client.js.map`，而它确实随包发布），`BUILD_INPUTS` 补上 `tsconfig.json`，失败文案改成两条并列成因（迭代顺序 / 路径依赖）。
- **参数行换行。** `panel.module.css` 的 `.canvasMeta` 加 `flex-wrap: wrap` 与 `row-gap: 4px`。`row-gap` 必须写在 `gap` 之后——`gap` 是简写，会把它覆盖掉。1440px 下短提示词与改前逐像素一致；长提示词（真实数据里最长 2257 字符）改前会被压成「本次生成 3 张」每行一个字，这一版顺带修好。
