# v1.30.2 — 接通 Nbility 的 MiniMax-H3（768P + 参考图上传）

Nbility 网关上的 `MiniMax-H3` 只有一个可用档位：**768P**。720P 和 1080P 都会被上游 400 拒绝：

```
MiniMax-H3 supports only 768P at normalizeRequest
```

而插件此前把 `MiniMax-H3` 归进通用的 `openai-video` 族，只提供 `480P / 720P / 1080P` 三档、默认 720P——**每一个请求都注定失败**，且报错发生在提交之后，用户看到的是一次「提交被拒」而不是「这个模型不接受这档分辨率」。

把档位补上之后，画布上的第二个问题暴露出来：图生视频仍然 400，因为参考图必须是公网 HTTPS URL，而插件只会发 data URI。官方契约里有一条 `POST /v1/media/uploads` 正好解决这件事——所以这一版是两件事：**多一个档位**，和**多一条上传腿**。

顺带把「分辨率档位散落在四处、各写一份」这个结构性原因一并消掉。

## 1. 档位类型加上 768P

`VideoResolution` 原本是 `'480P' | '720P' | '1080P'`。它不是营销话术的集合，而是**线上实际会发出去的字符串**，所以有模型只认 768P 时，类型就必须能说出 768P：

```ts
export type VideoResolution = '480P' | '720P' | '768P' | '1080P'
```

`RESOLUTION_RANK` 同步插入（`480P < 720P < 768P < 1080P`）。位置不是随手放的：`normalizeVideoResolution` 的降级语义是「取不超过请求档位的最高支持档」，768P 排在这里，1080P 的请求才会落到 768P（而不是掉到 720P），480P 的请求才会升到 768P，而 768P 本身原样保留。

## 2. MiniMax-H3 有了自己的协议族

一开始的判断是「只差一个分辨率档位」：实测 `POST https://api.nbility.ai/v1/videos` 确实也吃通用形状，网关自己把 `size` 归一化成 resolution、`seconds` 归一化成 duration。按这个判断，MiniMax-H3 只要窄化能力、留在 `openai-video` 族就够了。

但官方契约（`nbility.ai/docs/api/videos/minimax-h3`）里有第二个端点：`POST /v1/media/uploads`。参考图必须是**公网 HTTPS URL**，data URI 一律被拒（`Reference media requires a public HTTPS URL; uploads and Base64 are not supported`）——而这个上传端点正是把本地图变成公网 URL 的那条腿。插件只持有 data URL，通用形状里没有任何位置能放这次上传，所以 family 必须新增 `minimax`：

- **文生视频**：扁平 `{model, prompt, resolution: '768P', duration, ratio}`。
- **有参考图**：先 `POST /v1/media/uploads`（multipart `file`），拿到 1 小时后过期的 URL，再发 `content: [{type:'text',text}, {type:'image_url',image_url:{url},role}, …]`。
- `role` 按模式给：`image` → `first_frame`；`keyframe` → `first_frame` + `last_frame`；`reference` → 每张 `reference_image`（上游上限 9 张）。

窄化的能力写在 `describeVideoModel` 里、`isLikelyVideoModelId` 之前：`resolutions: ['768P']`（唯一能成功的档位）、`modes: ['text','image','keyframe','reference']`、`aspectRatios` 六档（16:9 / 9:16 / 1:1 / 4:3 / 3:4 / 21:9 实测全部被接受）。时长沿用默认的 5 / 10 秒：上游真实范围是 1..15 的整数，两个档位都在内。

上传腿的两个约束值得写下来，因为它们是**失败域**，不是参数：

- 上传有自己的诊断阶段 `video-upload`，失败码为 `video-upload-failed`（HTTP 层，带状态码与上游原话）或 `video-unreachable`（连接层）。提交阶段的 401 和上传阶段的 413 是完全不同的两件事，混在一个 phase 里就没法排查。
- 「上传 + 建任务」共用同一个 `SUBMIT_TIMEOUT_MS` 预算。否则一个卡住的上传会让整体耗时翻倍，而用户看到的只是一个没完没了的转圈。

同网关的 `doubao-seedance-2-0` 不受这个分支影响，仍走 seedance 族（实测它走的是**同一个** `/v1/videos`，但 768P 反而报 `unsupported Seedance resolution`——两个模型的能力刚好相反，这正是不能把它们合并成一个分支的原因）。

## 3. 四处内联的三档白名单收成一处

原来 `'480P' || '720P' || '1080P' ? … : '720P'` 这句话在四个地方各写一遍：

| 位置 | 改法 |
| --- | --- |
| `routes.ts` 的 `parseVideoRequest` | `parseVideoResolution(body.resolution)` |
| `routes.ts` 的 code-render probe | 同上（原先只认 480P/1080P，其余一律当 720P，会和面板显示不符） |
| `agent-video-tools.ts` 的工具入参 | 同上 + 参数说明改成「以所选模型接受的档位为准」 |
| `client/CanvasWorkspace.tsx` 的 fallback 列表 | `[...VIDEO_RESOLUTIONS]` |

新增 `parseVideoResolution(value, fallback = '720P')` 与 `resolutionRank()`，后者让 `video-director.ts` 里两份私有的 `['480P','720P','1080P']` 排序数组消失——规划器判断「只能降档不能升档」时用的就是目录里那份顺序，两处不会再各自漂移。

`VideoPanel.tsx:39` 那个 `RESOLUTIONS` 常量是死代码（全仓零引用），删除。

## 4. 分镜板的分辨率下拉框跟随模型

`storyboard-board.tsx` 原先硬编码三个 `<option>`，不看模型。现在从 `describeVideoModel(board.model)` 派生，模型未设置时给出全部档位。

一个取舍写在这里：**画布已有的、但模型不支持的档位不删掉，而是保留成一个选项**。用户打开一张旧画布时，把它文档里的值悄悄改写掉，比显示一个走不通的旧值更糟——前者不可见，后者看得见。

## 5. 本地渲染（code-render）给 768P 真实短边

`dimensionsFor` 原本 `480P → 480`、`1080P → 1080`、其余 → 720。768P 会落进 720 分支，probe 上报的像素数就和面板标签不一致。现在补上 768。

## 6. 200 + HTML 不再被当成接口响应

真机部署时发现一个跟本次需求直接相关的坑：渠道里 `apiUrl` 写成 `https://api.nbility.ai`（少了 `/v1`）时，上游返回 **200** 和它自己的首页 HTML。插件原本把非 JSON 的响应体截 300 字符塞进错误消息，用户看到的是：

```
submit failed: <!DOCTYPE html> <html lang="zh-CN"> <head> <meta charset="UTF-8"> …
```

现在识别出 HTML 就换成能指向原因的话：

> 返回的是网页而不是接口响应，通常是渠道的 API 地址少了路径（例如末尾缺 /v1）

这不是只为一个网关打的补丁：任何把站点根地址填进「API 地址」的渠道都会撞上同一件事，而「渠道地址少一段路径」恰恰是用户最难自己看出来的配置错误。新增 **V1m** 覆盖：假上游对提交回 200 + HTML，断言消息点名了原因、且不含任何 markup。

## 7. 工作流运行选项菜单关不掉

真机验收时用户报的：菜单点开之后「一直挂在上面，只能运行工作流他才关掉」——即唯一的关闭入口是那个会**真花钱提交任务**的菜单项。

根因不是漏了一个 `onClose`，而是关闭清单被抄了几份。底栏浮层有三个（背景、图片、工作流选项），每条关闭路径各自写一遍自己认识的那两个 state：

| 关闭路径 | 修复前 |
| --- | --- |
| 悬停离开（280ms 计时器） | 只清 background / image |
| Escape | 只清 background / image |
| 点画布空白处 | 只清 background / image |
| 打开其它底栏菜单 | 只互斥 background / image |
| 技能菜单打开时 | 只清 background / image / context … |

工作流菜单是后加的第三个，于是它成了画布上唯一关不掉的浮层。修法是**把清单收成一处** `closeDockMenus()`，五条路径全部改成调它；同时箭头按钮从「无条件重设坐标」改成 toggle，再点一次就收起。

`smoke-workflow.mjs` 锁的不是「某处有没有写 `setWorkflowMenu(null)`」——那正是漏掉时也照样能通过的写法——而是：

- `closeDockMenus` 存在且三件事都在里面；
- 全文件里 `setBackgroundMenu(null); setImageMenu(null)` 这种平行清单**只有一份**（抄几份就会漏几处）；
- 打开其它菜单时先收掉已开的浮层；
- 箭头按钮的 toggle 分支在。

反向用例两条：把工作流菜单从统一清单里摘出去 → 变红；某个入口又自己抄一份清单 → 变红。

真机复验（uireview 实例，1.30.2 部署后）：点开 → Esc 关；点开 → 点画布关；点开 → 再点箭头关；点开 → 打开背景菜单关（互斥）。四条全部按预期。

## 测试

`scripts/smoke-video.mjs` 新增三条，全部走离线假上游（假上游新增 `POST /v1/media/uploads` 分支，记录每次上传的文件名、mime、字节数）：

**V1l** — 目录与文生视频：

- `MiniMax-H3` 的 family 是 `minimax`、`resolutions` 恰为 `['768P']`、`modes` 恰为 `['text','image','keyframe','reference']`、六档画幅；同时确认 `doubao-seedance-2-0` 仍归 seedance、通用模型 `kling-v2-master` 仍保留三档（特化没有外溢）。
- 归一化：1080P / 480P / 未知词都落到 768P，768P 原样保留。
- 解析与排序：`parseVideoResolution` 的大小写、空白、缺省与未知词行为；`resolutionRank('720P') < resolutionRank('768P') < resolutionRank('1080P')`。
- 端到端：发一个 1080P 请求，断言线上 body 是 `{model, prompt, resolution:'768P', duration:5, ratio}`，且**不含** `content` / `size` / `seconds`；`uploads.length === 0`（文生视频不该触发上传）。

**V1n** — 三种参考图模式各跑一次（都传 1080P + 9:16 + 8 秒，证明归一化与模式无关）：

| 模式 | 上传张数 | 送达的 `role` |
| --- | --- | --- |
| `image` | 1 | `first_frame` |
| `keyframe` | 2 | `first_frame`, `last_frame` |
| `reference` | 3 | `reference_image` ×3 |

断言上传带 `Bearer`、mime 为 `image/png`、文件名为 `reference-N.png`、字节非空；`content[0]` 恰为 `{type:'text',text}`，媒体项 `image_url.url` 是假上游返回的 URL 而**不是** `data:` 开头。

**V1o** — 上传失败与其前置守卫：上传回 413 + `{error:{message:'file too large'}}` → 抛 `video-upload-failed`，消息含上游原话与 `HTTP 413`，且 `submits.length === 0`（没有建任务）；诊断里 `phase === 'video-upload'`、`url` 指向 `/v1/media/uploads`、`status === 413`、`hadAuth === true`。另断言空 prompt（`'   '`）抛 `video-bad-prompt` 且 `uploads.length === 0`——守卫必须在上传之前，否则用户为一次注定失败的提交付了上传流量。

## 真机验证（Nbility 网关，api.nbility.ai）

- 文生视频：`MiniMax-H3` / 768P / 5 秒 / 16:9 → `queued` → `in_progress`（progress 0/33/99）→ `completed`，顶层 `url` 指向 COS 上的 mp4，1,859,764 字节。5 秒片子约 3 分钟。
- 图生视频：512×512 PNG 上传换 URL → 以 1080P / 9:16 提交（1080P 是故意的，用来证明归一化）→ 成功，1,628,276 字节；换 768P / 9:16 再跑一次，1,342,898 字节、208 秒。
- 拦截 fetch 核对插件真正发出的 multipart：`content-type: multipart/form-data; boundary=…`、`authorization: Bearer sk-kj…`、首部 `Content-Disposition: form-data; name="file"; filename="reference-1.png"` + `Content-Type: image/png`，正文 94,788 字节、首字节是真实 PNG 头。
- 720P、1080P、以及 `size: "720P"` 的扁平写法，全部被上游 400 拒绝，报错原文记录在注释与测试里。

## 边界如实说明

- 768P 是**上游唯一可用的档位**，不是「推荐档位」。面板上它会是 MiniMax-H3 唯一可点的按钮。
- 参考图走 `POST /v1/media/uploads` 换公网 URL，换来的 **URL 1 小时后过期**：提交任务必须紧接着做，不能先攒一批图再慢慢提交。插件在一次 `SUBMIT_TIMEOUT_MS` 预算内完成「上传 + 建任务」，就是为了不让 URL 在自己的流程里老掉。
- 上传的大小/格式边界由上游裁定，插件不做客户端预检（图片 ≤30 MB、边长 256–5760 px；视频 ≤50 MB；音频 ≤15 MB）。失败会带上游原话回来。
- 取消（`REMOTE_CANCEL`）仍是 unsupported：网关没有实测的取消端点，插件不伪造一个。
- `doubao-seedance-2-0` 在同一网关上走同一个 `/v1/videos`，但插件会按 seedance 族发 `content[]` 到 `/contents/generations/tasks`——该路径在此网关上一律 `Invalid URL`。也就是说**这个模型在这个网关下仍未接通**，本版没有修它（不在本次需求范围内，且需要单独验证 Seedance 在那个网关上的真实形状）。
- 首尾帧的宽高比必须相差 ≤2%（上游约束）；插件不在本地校验，冲突时由上游拒绝。
