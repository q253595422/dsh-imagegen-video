# v1.30.2 — 支持只收单一分辨率档位的视频模型（MiniMax-H3 / Nbility）

Nbility 网关上的 `MiniMax-H3` 只有一个可用档位：**768P**。720P 和 1080P 都会被上游 400 拒绝：

```
MiniMax-H3 supports only 768P at normalizeRequest
```

而插件此前把 `MiniMax-H3` 归进通用的 `openai-video` 族，只提供 `480P / 720P / 1080P` 三档、默认 720P——**每一个请求都注定失败**，且报错发生在提交之后，用户看到的是一次「提交被拒」而不是「这个模型不接受这档分辨率」。

本版修的就是这件事，同时把「分辨率档位散落在四处、各写一份」这个结构性原因一并消掉。

## 1. 档位类型加上 768P

`VideoResolution` 原本是 `'480P' | '720P' | '1080P'`。它不是营销话术的集合，而是**线上实际会发出去的字符串**，所以有模型只认 768P 时，类型就必须能说出 768P：

```ts
export type VideoResolution = '480P' | '720P' | '768P' | '1080P'
```

`RESOLUTION_RANK` 同步插入（`480P < 720P < 768P < 1080P`）。位置不是随手放的：`normalizeVideoResolution` 的降级语义是「取不超过请求档位的最高支持档」，768P 排在这里，1080P 的请求才会落到 768P（而不是掉到 720P），480P 的请求才会升到 768P，而 768P 本身原样保留。

## 2. MiniMax-H3 单独特化，但仍走通用族的线上格式

family **没有**新增。实测 `POST https://api.nbility.ai/v1/videos` 接受的就是通用形状，网关自己把 `size` 归一化成 resolution、`seconds` 归一化成 duration、`aspect_ratio` 归一化成 ratio，回读也是这三个字段。所以 `submitBody` 一个字都不用改。

窄化的是**能力**，写在 `describeVideoModel` 里、`isLikelyVideoModelId` 之前：

- `resolutions: ['768P']` — 唯一能成功的档位。
- `modes: ['text']` — 参考图只接受公网 HTTPS URL（`Reference media requires a public HTTPS URL; uploads and Base64 are not supported`），而本插件只会发 data URL。与其让图生视频在线上被拒，不如面板上就不提供这个模式。
- `aspectRatios` 六档 — 16:9 / 9:16 / 1:1 / 4:3 / 3:4 / 21:9 实测全部被接受。

时长沿用默认的 5 / 10 秒：上游真实范围是 1..15 的整数，两个档位都在内。同网关的 `doubao-seedance-2-0` 不受这个分支影响，仍走 seedance 族（实测它走的是**同一个** `/v1/videos`，但 768P 反而报 `unsupported Seedance resolution`——两个模型的能力刚好相反，这正是不能把它们合并成一个分支的原因）。

## 3. 四处内联的三档白名单收成一处

原来 `'480P' || '720P' || '1080P' ? … : '720P'` 这句话在四个地方各写一遍：

| 位置 | 改法 |
| --- | --- |
| `routes.ts` 的 `parseVideoRequest` | `parseVideoResolution(body.resolution)` |
| `routes.ts` 的 code-render probe | 同上（原先只认 480P/1080P，其余一律当 720P，会和面板显示不符） |
| `agent-video-tools.ts` 的工具入参 | 同上 + 参数说明改成「以所选模型接受的档位为准」 |
| `client/CanvasWorkspace.tsx` 的 fallback 列表 | `[...VIDEO_RESOLUTIONS]` |

新增 `parseVideoResolution(value, fallback = '720P')` 与 `resolutionRank()`，后者让 `video-director.ts` 里两份私有的 `['480P','720P','1080P']` 排序数组消失——规划器判断「只能降档不能升档」时用的就是目录里那份顺序，两处不会再各自漂移。

`VideoPanel.tsx:39` 那个 `RESOLUTIONS` 常量是死代码（全仓零引用），删除。

## 4. 分镜板的分辨率下拉框跟随模型

`storyboard-board.tsx` 原先硬编码三个 `<option>`，不看模型。现在从 `describeVideoModel(board.model)` 派生，模型未设置时给出全部档位。

一个取舍写在这里：**画布已有的、但模型不支持的档位不删掉，而是保留成一个选项**。用户打开一张旧画布时，把它文档里的值悄悄改写掉，比显示一个走不通的旧值更糟——前者不可见，后者看得见。

## 5. 本地渲染（code-render）给 768P 真实短边

`dimensionsFor` 原本 `480P → 480`、`1080P → 1080`、其余 → 720。768P 会落进 720 分支，probe 上报的像素数就和面板标签不一致。现在补上 768。

## 测试

`scripts/smoke-video.mjs` 新增 **V1l**，全部走离线假上游：

- 目录断言：`MiniMax-H3` 的 family 仍是 `openai-video`、`resolutions` 恰为 `['768P']`、`modes` 恰为 `['text']`、六档画幅；同时确认 `doubao-seedance-2-0` 仍归 seedance、通用模型 `kling-v2-master` 仍保留三档（特化没有外溢）。
- 归一化断言：1080P / 480P / 未知词都落到 768P，768P 原样保留。
- 解析与排序：`parseVideoResolution` 的大小写、空白、缺省与未知词行为；`resolutionRank('720P') < resolutionRank('768P') < resolutionRank('1080P')`。
- 端到端：发一个 1080P 请求，断言线上 body 是 `size: '768P'`（而非 `resolution`）、`seconds` 是字符串 `'5'`、`aspect_ratio` 正确、text 模式不带 `image`、轮询用网关返回的 `task_…` id。

38 项全绿（含此前 35 项）：V1l 覆盖 768P 特化与端到端提交，V1m 覆盖 200 + HTML 的错误解释。

## 真机验证（Nbility 网关，api.nbility.ai）

- 提交 `MiniMax-H3` / 768P / 5 秒 / 16:9 → `queued`，轮询 `in_progress`（progress 0/33/99）→ `completed`，顶层 `url` 指向 COS 上的 mp4。5 秒片子约 3 分钟。
- 720P、1080P、以及 `size: "720P"` 的扁平写法，全部被上游 400 拒绝，报错原文记录在注释与测试里。
- 参考图 data URI 被拒；公网 HTTPS URL 可（本版因此不提供图片模式）。

## 6. 200 + HTML 不再被当成接口响应

真机部署时发现一个跟本次需求直接相关的坑：渠道里 `apiUrl` 写成 `https://api.nbility.ai`（少了 `/v1`）时，上游返回 **200** 和它自己的首页 HTML。插件原本把非 JSON 的响应体截 300 字符塞进错误消息，用户看到的是：

```
submit failed: <!DOCTYPE html> <html lang="zh-CN"> <head> <meta charset="UTF-8"> …
```

现在识别出 HTML 就换成能指向原因的话：

> 返回的是网页而不是接口响应，通常是渠道的 API 地址少了路径（例如末尾缺 /v1）

这不是只为一个网关打的补丁：任何把站点根地址填进「API 地址」的渠道都会撞上同一件事，而「渠道地址少一段路径」恰恰是用户最难自己看出来的配置错误。新增 **V1m** 覆盖：假上游对提交回 200 + HTML，断言消息点名了原因、且不含任何 markup。

## 边界如实说明

- 768P 是**上游唯一可用的档位**，不是「推荐档位」。面板上它会是 MiniMax-H3 唯一可点的按钮。
- 参考图只支持公网 HTTPS URL，而插件没有上传通道（`/v1/files`、`/v1/uploads`、`/v1/assets` 均不存在），所以图生 / 首尾帧 / 参考生三种模式对 MiniMax-H3 完全不可用。要支持，得先有一条把本地图变成公网 URL 的链路，本版没做。
- 取消（`REMOTE_CANCEL`）仍是 unsupported：网关没有实测的取消端点，插件不伪造一个。
- `doubao-seedance-2-0` 在同一网关上走同一个 `/v1/videos`，但插件会按 seedance 族发 `content[]` 到 `/contents/generations/tasks`——该路径在此网关上一律 `Invalid URL`。也就是说**这个模型在这个网关下仍未接通**，本版没有修它（不在本次需求范围内，且需要单独验证 Seedance 在那个网关上的真实形状）。
