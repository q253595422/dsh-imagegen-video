# v1.15.2 — 视频取片支持 `/content` 回退

一句话概括：任务已经渲染完成、轮询却因为没有 URL 被判失败的情况，现在会真的把成片取回来。

## 为什么

`readPoll()` 只在轮询响应体的六个字段里找视频地址，找不到就把任务判成失败，弹出「视频任务已完成但未返回视频地址」。

但 OpenAI 官方的视频 API——以及照抄它的 OpenAI 兼容网关——在终态里**不返回任何 URL**：`status` 走到 `completed`，成片只通过 `GET /v1/videos/{id}/content` 以二进制流提供。于是上游明明渲染好了，插件这边报失败，用户拿不到片子；对按次计费的上游来说，这次调用是白花的。

这不是某一个网关的私有行为，所以修在上游协议这一层，而不是给某个渠道加特判。

## 做了什么

- **轮询结果能表达两种取片来源**：响应体里有 URL 就照旧用 URL（优先级不变，它通常指向 CDN，比回源更省事）；没有任何 URL 但状态已完成时，轮询把 `/content` 端点作为片源返回，而不是判失败。
- **下载沿用同一条腿**：`/content` 的字节走原有的下载函数，同源鉴权转发、MIME 推断、体积上限全部照旧生效——没有为它新开一条绕过这些约束的通道。
- **失败仍然是失败**：`/content` 返回 404 之类的错误时，报的是下载环节的真实错误，不会静默当作成功。任务真失败（`failed` / `expired`）的判定也完全没变。

## 验证

- `scripts/smoke-video.mjs` 新增两条用例：一条让 mock 上游只给 `/content`、响应体不含 URL，断言成片被取回；一条让 `/content` 返回 404，断言报出的是下载错误而不是「已完成但无地址」。
- `scripts/verify-negative.mjs` 加了对应的缺陷注入：把回退移除后，新用例会变红，确认这两条测试确实在看这件事。
- `node scripts/smoke-video.mjs` 全绿。

## 影响面

只影响「轮询响应体里没有视频地址」的分支；有 URL 的渠道走的是原来那条路径，行为不变。

Closes #9.
