# v1.30.1 — 三个「已经实现但没有入口」的功能补上界面

本版不加新能力，只把此前写完却没人能点到的三处接到界面上，并补上它们一直缺的测试。三个功能各自的逻辑早就在仓库里，缺的是入口和「关掉之后真的失效」的证据。

## 1. 画布整图导出 / 导入

后端两条路由（`/canvas/bundle/export`、`/canvas/bundle/import`）和 `buildCanvasBundle` / `parseCanvasBundle` 早就写好了，但客户端**零引用**——整个功能从外面看不到。

现在画布顶栏、全屏按钮右侧两个入口：

- **导出**：把画布文档连同每个图片资产的字节打成一个 JSON 文件下载。片段（视频）是**引用而非拷贝**——一个包捎上整段视频会把体积推到不可用的量级。所以带片段的画布导出时一定会产生 `unresolved`，这不是失败：文档和全部静图都是完整的，提示只是告诉用户**换台机器后哪一部分打不开**，并且按 `kind` 分开计数——`asset` 是图片字节缺失，`video` 是片段没进包，两者对用户的意义不同。
- **导入**：**总是创建新画布**、分配新 id，绝不覆盖已有画布。导出者很可能就是导入者，让他能把自己的原画布冲掉不是「方便」是危险。

两处实现细节值得记下：

- 导出用 `Blob` + `createObjectURL`，并在 `finally` 里 `revokeObjectURL`。几百 MB 的 blob 留在文档生命周期里是实打实的内存泄漏。
- 导入**刻意不走 `seedDocument`**。那个函数会给节点为空的画布注入一对 text + config 起点节点——对新画布是对的，对导入是错的：导出一张空画布应当收回一张空画布，而不是被悄悄塞进两个用户没放过的节点。
- 导入后必须自己把新画布插进 `projects`。导入路由不返回项目列表，不插的话下拉里没有它，而 `document.id` 已指向它，`currentProject` 查不到会让收藏/删除按钮落在错误状态。

## 2. 工作流：续跑、强制重跑、层内并发

执行器三项能力全都有（`reuse`、`rerun`、`maxParallel`），但调用点把单节点那层的 `reuse` 写死成 `true`，另外两项根本没传。

现在底栏工作流按钮旁边多一个箭头，打开三个开关：

- **复用上次产物**（默认开）——关掉时全链重新提交，按节点数计费。
- **强制重跑选中节点**（默认关）——闭包由执行器自己算，界面只交出起点。
- **层内并发**（默认开）——关掉时传 `maxParallel: 1`。

三个默认值都等于升级前写死的行为，所以**直接点主按钮与旧版完全一致**。这是我没有采纳「把运行塞进菜单」的原因：那会让常用路径每次都多点一下，换来的只是「先看见复用是开着的」，而默认值本来就保证了这一点。

> **「复用」有两层，必须同时受控。** `runWorkflowPlan` 的 `reuse` 数组（节点级不提交、记 cached）与 `runWorkflowNode` 的 `reuse` 布尔闸门（`hasProduce` 时短路成 cached）是两回事。只关前一层的话，节点仍会在后一层被短路：用户看到开关关了，实际什么都没重跑。

## 3. 测试：补上「写错了也不会有任何测试变红」的那一层

这是本版真正花时间的地方。

执行器层原本覆盖得不错，缺的是**界面到底有没有把参数传下去**。这类故障不会让任何执行器测试变红——开关照常可点、执行器照常正确，只是值停在了半路。

新增两处：

- **`smoke-workflow.mjs`** 补执行器两个真实边界：`maxParallel=2` 时同时在飞的数量**恰好**是 2（此前只测了 1 和「不限」两个极端，而 2、3 才是用户真会填的值）；`0`、`-3`、`1.5`、`NaN` 一律按 1 处理（漏掉归一会让限流宽度变成 0，一个节点都不派发，整条工作流静默挂住）。
- 同一文件新增接线断言：三个开关的默认值、两处 `reuse` 同受控、`maxParallel` 方向、重跑只交起点、`useCallback` 依赖数组含三个 state。
- **`smoke.mjs`** 在真实 jsdom 渲染的画布上断言两个按钮确实在顶栏、`accept` 正确、且没有被打上 `data-dock-item`（那个属性是底栏瓦片的标记，布局守卫会逐个量宽度）。

反向验证：把单节点闸门改回字面量 `true`、把归一拆掉、把导出按钮的文案改错，各自都让对应断言变红；还原后恢复绿色。

## 真机走查（1.30.1 部署到 uireview 后实测）

导出/导入不是只验到接线，做完了一次完整往返：

- 源画布 16 个节点、4 个图片节点、3 个真实资产（1.7MB + 1.8MB + 76KB）。导出 **538ms**、**4.78MB**，包结构 `format / version / exportedAt / title / document / assets / unresolved` 齐全，正确报出 1 条 `{kind:'video', reason:'clip-not-bundled'}`——画布里有 7 个视频节点，包只带了那 1 条没成片的引用。
- 导入 **99ms**，新 id、16 个节点、`unresolved` 原样透传，画布列表 +1。逐字段比对源与新画布：**`JSON.stringify` 完全相等**，3 个资产的 `assetId` 与字节数一字不差。
- 走界面按钮（`<input type=file>`）再跑一遍：文件选择器触发、解析、导入、新画布插入都正常，提示文案是「已导入为「未命名画布」 有 1 个片段引用了原机器上的视频，这里打不开。」

顺带确认了两件原本只是「应该如此」的事：

- **导入不覆盖**：源画布 id 与新画布 id 不同，导入后列表只增不减。
- **空资产不被伪造**：源画布那个 `assetId` 为空的图片节点（图片描述技能的产物），导入后仍是空，没有被塞进一个假资产。

工作流三个开关在真机上也逐个看过了：菜单三项齐全、默认值对（复用开 / 重跑关 / 并发开）、禁用态文案正确、长提示文案不被压扁。

## 边界如实说明

- 大画布导出期间界面只有按钮变灰，没有百分比。几百 MB 的极端体积没有实测过。
- 导入不做版本兼容转换：包的 `version` 高于当前插件时由 `parseCanvasBundle` 拒绝，没有「尽力读一下」的路径。
- 导入时若已有同名画布，两份会并列存在（导入总是新建），没有「重命名并覆盖」的选项。
