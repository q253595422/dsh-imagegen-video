# v1.23.1 · 服饰穿戴：草稿读失败不再把整张表单锁死

> 各版本改动见 [CHANGELOG.md](../../CHANGELOG.md)。

这一版只修「服饰穿戴」里的一个交互缺陷：**草稿读不到的时候，整张表单变成死的**。
用户看到的症状是「角色搭配点了没反应」。

## 症状与根因

面板在草稿读回来之前会把整张 `<fieldset>` 禁用——这本身是对的：迟到的旧草稿会覆盖
用户刚做的编辑，所以读的过程中先不让改。

问题出在**读失败**的情况。失败后 `draftLoaded` 永远是 `false`，于是：

- 模式切换（商品试穿 / 角色搭配）、图库入口、上传按钮**全部永久点不动**；
- 提示只有一句「无法读取搭配草稿」，没有任何说明这些控件为什么点不了；
- 重试加载成功后，用户之前的编辑会被磁盘上的旧草稿整体覆盖。

## 改了什么

**只有「正在读」这一小段窗口锁表单。** 读失败后表单解锁，可以继续选素材、切模式、
调场景与模型。提示同时补一句后果：

> 无法读取搭配草稿：…。请重试加载。**现在仍可继续编辑，但草稿要等重新加载成功才会保存。**

保存本身仍然有 `draftLoaded` 闸，所以放开编辑不会盲覆盖磁盘上的旧草稿。

**重试成功不覆盖眼前的编辑。** 读失败期间改过配方（模式、素材、场景、模型）就记为已编辑，
此时重试或重新挂载拿到的旧草稿不再 `setRecipe` 覆盖它，只解除保存闸。

**预览也不再等草稿。** 「准备参考图预览」只在本机下载并排版参考图，既不写草稿也不调模型，
原来却要求 `draftLoaded`——于是草稿读失败时提交按钮看着能点、点下去什么都不发生。
这和锁死表单是同一类缺陷，一起修掉。

## 为什么离线套件没抓到

E1 的 jsdom 沙箱没有应答 `/api/dsh-imagegen/outfit/draft`，请求落到 catch-all 抛错，
`draftLoaded` 因此是 `false`，整个表单被禁用。

jsdom 的 `dispatchEvent` **仍会触发处理器**，所以「点角色搭配 → aria-checked 翻转」这条
断言在沙箱里看起来是有效的；而真浏览器会把落在 disabled 控件上的点击直接丢掉。也就是说
这条检查一直在禁用控件上点空气。

此外点击后的断言紧跟着 `dispatchEvent` 读 DOM，而 React 在同一个 tick 内批量更新——那只在
更新恰好同步冲刷时才会通过，所以这条检查在不同沙箱搭法下会红绿摇摆。

三处一起改：

| 改动 | 目的 |
| --- | --- |
| stub 补 `/outfit/draft` 应答 | 让沙箱里的表单真的可用 |
| 新增「表单与模式按钮在点击前是启用的」两条断言 | 「控件是死的」不能再伪装成「处理器有问题」 |
| 点击后等一次重渲染再读 | 断言渲染后的树，而不是渲染前的 |

反向用例新增一条：把 `formLocked` 改回恒禁用，上述断言必须变红（实测 1/1 变红）。

## 检查

- `pnpm run typecheck`：exit 0。
- `pnpm test`（独占运行）：274 项通过，0 失败。
- 真浏览器（headless Chromium，把草稿路由注入 500）：表单未禁用，点「角色搭配」后
  `aria-checked` 由 `false` 变 `true`，说明文案同步切换，错误提示带上了「仍可继续编辑」。
- `verify-negative.mjs smoke "permanently disabled fieldset"`：RED as expected。

## 已知边界

- 草稿读失败期间做的编辑只在**内存里**。如果一直没能重新加载成功就关掉面板，这些编辑
  不会落盘——这是刻意的：读不到旧草稿时写盘会盲覆盖。
- 这一版不改变「草稿读失败」本身的发生概率。它会失败通常是宿主路由或磁盘问题，
  面板现在能如实说明并允许继续工作。
