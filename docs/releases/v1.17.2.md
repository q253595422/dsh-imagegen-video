# v1.17.2 — Windows 上 ffmpeg 找得到、失败不再被记成通过、视频任务重启不丢

一句话概括：Windows 用户第一次能真正用上视频链路；同时修掉一处会让「功能全废但测试全绿」的测试缺陷，并补上 v1.17.1 之后未发布的五条视频可靠性修复。

## 为什么

v1.17.1 发布后收到两份 Windows 环境的报告。第一份说所有依赖 ffmpeg 的能力全部拒绝运行——画布拼接、时间线、代码渲染、字幕，一个都跑不了；但 `where ffmpeg` 明明有输出，目录也在 PATH 里。

第二份更值得注意：`npm test` 在 Windows 上跑不绿，11 条独立缺陷。其中最后一条解释了第一份为什么能藏那么久——

> `check(name, fn)` 看到 `fn` 正常返回就记 PASS。而缺 ffmpeg 的用例是 `return` 而不是 `skip()`，所以 C5（产出可播放 MP4）和 C7（渲染片段可被拼接）在缺工具的机器上**一直在报告里显示「通过」，实际一行没执行**。

也就是说：**测试全绿，功能全废**。这一版把这两件事一起修掉。

## 做了什么

### ffmpeg 发现：四份实现收敛成一份

同一个问题在仓库里有四份彼此独立的答案，且没有一份能在 Windows 上成立：

- `localVideoToolDirs()` 只列四个 POSIX 目录（`~/.local/bin`、Homebrew、`/usr/local/bin`、`/usr/bin`），Windows 上一个都不存在，且**从不查 PATH**——而 winget、scoop、官方 zip 全都靠加 PATH 安装。
- `findTool()` 用裸名拼接，`path.join(dir, 'ffmpeg')` 永远匹配不到 `ffmpeg.exe`。
- `locateFfmpeg()` 是第二份候选列表，和上面不共享任何代码。两份列表已经漂了：`/snap/bin` 只在其中一份里。
- 两个测试脚本又各自内联了一遍。

最关键的证据来自报告者：先改完 `video-tools.ts` 和 `code-render.ts` 之后，`smoke-compose` 的跳过信息里**已经列出了 `D:\Program Files\Kdenlive\bin`**，却仍然判定找不到——因为它在用自己那份逻辑。只修看得见的一处，症状会换个面貌回来。

现在 `locateFfmpeg()` 只剩一行 `return findTool('ffmpeg')`，两个测试脚本也改为调用宿主自己的 `findTool()`。`FFMPEG_PATH` / `FFPROBE_PATH` 由共享的查找处理，所以「手工填了路径只修好一半功能」这个现象不会再有。

`findTool` 在 win32 上同时试 `name` 与 `name.exe`，并把可执行性判断退化为 `isFile()`——`X_OK` 在 Windows 上是基于只读属性的模拟，对普通文件是否返回成功并不稳定。

### 测试里「跳过」不再冒充「通过」

`smoke-code-render` 里三处 `return` 静默跳过全改成 `skip()`：

- **C5**（产出可播放 MP4）、**C7**（渲染片段可被拼接）——原先缺 ffmpeg 时记 PASS。
- **C4c** 顺带挖出来的反向问题：它同样依赖 ffmpeg，但原来没有守卫，在缺工具的机器上拿到 `render-no-ffmpeg` 而不是 `render-timeout`，于是**报红**。同一台机器，一边假绿一边假红。
- C5 里还有一层更隐蔽的：`probeWithFfprobe()` 返回 undefined 时整段 ffprobe 断言被 `if` 跳过，于是「PLAYABLE」这个名字在有 ffmpeg、没 ffprobe 时是没人验证过的断言。现在无 ffprobe 就整个 C5 记 SKIP，有则硬断言。

汇总行固定打印 `N skipped: <名字列表>`，有跳过时通过行写 `, N not exercised`。跳过仍然退出 0——跳过不等于失败。

### 其余 Windows 兼容（同一份报告的 11 条）

| 位置 | 问题 |
|---|---|
| `verify-tracked` | `path.relative` 返回反斜杠，`git ls-files` 返回正斜杠，150 个已跟踪文件全被判成「不在仓库里」 |
| `verify-reproducible` | `pnpm` 在 Windows 是 `.cmd` shim，Node 不允许 `execFile` 执行；改跑 pnpm 自己的 JS 入口 |
| 同上 | 目录符号链接在 Windows 需要特权，改用 `'junction'` |
| 同上 | `cpSync({recursive:true})` 在 Windows 上让进程以退出码 127 静默消失，改手写递归拷贝 |
| `smoke-storyboard`、`ppt-browser-test` | `URL.pathname` 不是文件路径，Windows 上得到 `/E:/%E3%80%90...` |
| `verify-pack` | `--ignore-scripts` 在 pnpm 10 被移除；tar/du 把盘符冒号当成远程主机；tar 列表按 `\n` 切会留下 `\r` |
| `verify-ui-contracts` | `node_modules/.bin/tsc` 在 Windows 是 POSIX shell 脚本，改跑 TypeScript 自己的 JS 入口 |
| `headless-chrome` | 没有 Windows 浏览器候选，三个浏览器守卫在 Windows 上永久 SKIP |
| 全部守卫 | 跨行正则写死 `\n`，而 Git for Windows 检出 CRLF；改为读取时统一归一 |

`findChrome()` 补上了 Chrome / Edge / Chromium 的 Windows 路径。完整版浏览器需要 `--headless=new` 而 `chrome-headless-shell` 不认它——按可执行文件名判断，放在 `launchChrome()` 内部，调用方零改动。

CRLF 那一项做了两层：脚本侧新增 `scripts/lib/source-text.mjs`（读源码统一归一），仓库侧新增 `.gitattributes`（`* text=auto eol=lf`）。归一放在读取处而不是逐个正则加 `\r?`，是为了让以后新写的正则默认就是对的。

### v1.17.1 之后未发布的视频可靠性修复

`v1.17.1` 的 tag 停在 10-25 12:19，但之后还有几条修复从未进入任何发布，这次一并带上：

- **重启后重连正在渲染的任务。** 队列原本只在内存里，也不带服务商自己的任务 id，所以重启后无法回到一个已经付过费的渲染。现在提交时持久化该 id（只存索引，不存帧），重启后的第一次轮询重连**同一个**远端任务并继续下载，而不是重新提交、重新扣费。任何终态都会清掉记录，索引不会无限增长。
- **取消只停本地，不编造远端请求。** 各协议族都没有实测过的取消端点——OpenAI 的 `DELETE /videos/{id}` 删的是已完成/已失败的视频，不取消运行中的，而它所属的 Sora API 已于 2026-09-24 关停。所以每个族都报 `unsupported`，面板如实说「渲染可能仍在运行并计费」，而不是假装扣费已停。
- **工作流 fail-fast 不再误伤独立分支。** 任一节点失败曾被视为整轮结束，杀掉无关分支；现在只阻塞失败节点自己的下游闭包，独立分支跑完时状态报 `partial`。
- **分镜 carry 重跑会标脏下游。** 从旧尾帧构建的片段原本会静默失配；现在这些镜头标记为 stale（文件保留）并退出拼接。
- **模型别名跨渠道歧义。** 同名别名原本解析到先遇到的那个渠道，显式选择可能被覆盖并计到另一把 key 上；现在显式 `channelId` 优先。

## 验证

- `tsc` 0 错，`tsdown` 构建通过，`verify-reproducible` 跨目录逐字节一致。
- 全量 `pnpm test` **EXIT=0**，零 `FAIL`；含 `SMOKE TEST OK`、`16/16 code-render checks pass`、`0 skipped: the real ffmpeg encode path ran`、`timeline: 24 checks ok`、`cast: 13 checks ok`、`T6 PART B: 34 PASS / 0 FAIL`、`FRAME GRAB VERIFIED`、`UI CONTRACTS VERIFIED`。
- **Windows 规则的验证方式**：`findTool` 的 `platform` / `env` / `home` 全部做成可注入，于是一个临时目录加一条假 PATH 就能在 macOS 上证明 `.exe` 后缀、分号分隔、PATH 参与查找、覆盖优先级、执行位差异——15 项断言全过。`home` 可注入不是洁癖：本机 `~/.local/bin/ffmpeg` 真实存在且正是第一个候选目录，不隔离的话所有断言都会「通过」，只是原因不对。
- **「跳过真的显示成 SKIP」是实测的**，不是推断：`HOME=<空目录> FFMPEG_PATH= node scripts/smoke-code-render.mjs` 得到三行 `SKIP`、`13/16 pass, 3 not exercised`，退出码 0。
- 反向用例新增三条（`.exe` 后缀、PATH 参与、CRLF 归一），均确认会变红。CRLF 那条注入的是「转成 CRLF」而不是「去掉归一」——在 LF 检出上去掉归一是个 no-op，会报 FALSE GREEN。
- 一次 CI 红而本地绿的插曲：最初断言「POSIX 查找必须什么都找不到」，而 CI 会在跑测试前把 ffmpeg 装进 `/usr/bin`，POSIX 候选里正好有它。断言测的是机器不是规则，已收窄为「绝不把 `.exe` 当工具」。

## 已知缺口

- **Windows 上的行为未在真机实测。** 这台开发机是 macOS。纯语义修复（路径分隔符、`fileURLToPath`、换行归一）可直接推断成立；`pnpm` 入口、junction、tar 盘符、`.bin/tsc`、Chrome 候选这几条是依据报告者实测的根因写的，机理对得上但没有在 Windows 上跑过。报告者已表示会在那边重跑确认。
- `verify-native-ui.mjs` 的 DSH token 检查在 Windows 上仍然跳过：宿主包在 `app.asar` 里，不是可扫描目录，需要解包才能做文本匹配。这条不算 bug，未动。
- 缺工具时跳过仍然退出 0。是否让 `skip` 数量 > 0 时返回非零码，留给 CI 显式决定，本版没有启用。
