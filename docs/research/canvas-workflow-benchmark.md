# 创作画布对标：从第一条链路到可交付成果

调研日期：2026-11-18。

**建议先修保存与恢复，再做大图导航和交付复用。** 本项目已有示例、节点搜索、历史与便携包，先用代表场景验证它们是否在大图、切换、断线与失败时可靠，不复刻竞品工具栏。

## 本项目优先级与验收门槛

调研时的[画布入口](../../src/client/CanvasWorkspace.tsx)已包含示例、节点搜索、编辑历史、保存重试和画布包导入/导出。基线代码的保存冲突分支读取服务端最新 revision，再把原整图快照提交一次；这不是合并，若另一窗口已改其他节点，自行换 revision 有覆盖风险。需用真实双页面和可控延迟复现，不能拿这个观察当作已经量到的丢数据率。

| 优先 | 交付 | 固定场景与目标（不是实测） |
| --- | --- | --- |
| P0 保存与恢复 | 让编辑结果、保存状态与宿主确认一致；遇到断线或真实冲突保留本地改动，给重试或恢复副本入口，不静默覆盖。正常路径不增加确认。 | 两个页面同时打开 A，各改不同节点；乱序/延迟返回首笔保存；编辑后立即切到 B；保存失败后刷新、重新连接；验证服务端/待恢复内容和操作页面，**0 笔静默丢失、0 次串页或误报保存成功**。只有服务端确认或一份可读取的草稿才可称保住。 |
| P1 定位与编辑响应 | 节点搜索、列表与画布聚焦走同一条定位路径；复杂图可按视口减少节点主体、媒体预览和连线的工作，不能牺牲框选、缩放、撤销和连线正确性。 | 固定新品短片：12 节点（基本链路）、200 节点（含图/视频/分组/重名）、1,000 节点（压力）。从已知名称到定位不超过 3 个操作阶段：开搜索、输入、确认，固定图上 100% 命中指定 ID；200 节点真实指针连续拖动/平移的帧间隔 p95 目标 ≤33 ms，搜索输入到结果 p95 目标 ≤100 ms；压力档记录数字与卡顿，不把 200 档的目标偷换成压力档的结论。 |
| P2 复用与交付 | 在既有画布包和输出路径上做图区块复用、依赖预检和明确区分工作流文件与成品。优先争取「无需平台账号可移交可编辑流程」，而非比模型总数。 | 从示例改实际提示词、连接参考图 → 生图 → 图生视频 → 合成，预览并下载结果；同一图导出带素材的画布包、导入隔离项目后核对节点、角色边、素材和输出，再换一个输入复跑。断开参考素材和注入一次生成失败，定位可修复项、重试时不重跑已完成且未变的分支（仅在产品明确支持该语义后纳入通过标准）；成片和可编辑包不能混淆。 |

测量时复用同一浏览器版本、硬件、视口、固定数据、输入节奏和故障顺序，分别跑基线与改后。每次分开记录键盘/指针动作数、响应 p50/p95、失败次数，以及最终磁盘/页面断言；搜索响应与生成等待分开，固定素材/任务服务的回放与外部真实模型分开。用 ≥20 次轻量交互试验报告分位；性能结论不使用 jsdom 或区分不了渲染阶段的网络计时。只有竞品也在同一工作负载、交互与环境下测完，才报告「快于该竞品」；其余只说功能差异或本项目改动前后的收益。

## 实测：200 / 1000 节点画布（2026-11-18）

复跑：`node scripts/benchmark-canvas-interaction.mjs --url <宿主地址> --out <json>`。脚本自己起无头 Chrome、自己导入同规模的画布包，只量不写任何画布目录。**必须在无头窗口里量**——IDE 里那个自动化浏览器窗口的 rAF 被节流到约 2.5 fps（实测空闲帧间隔 380 ms），拿它量任何交互都会得出「每次缩放 800 ms」的假数，且与节点数无关（12 个节点也一样）。

固定负载：混合 text / config / storyboard；视口 k=0.5；每 25 个一张同名卡（`重名节点 N`）用于验证搜索落到确定 id；视口约 722×330（三栏工作室下的窄画幅，最不利的一档）。

| 指标 | 12 节点 | 200 节点 | 1,000 节点 |
| --- | --- | --- | --- |
| 导入到全部挂载 | 0.35–1.9 s | 0.35–0.9 s | 0.75–2.1 s |
| 画布内 DOM 元素 | 968 | 13 524 | 62 877 |
| 缩放一次 click→paint p50 / p95 | 59 / 1136 ms（首轮含冷启动） | **38 / 46 ms** | 172 / 444 ms |
| 平移帧间隔 p50 / p95 | — | **16.7 / 56 ms** | 43 / 290 ms |
| 搜索：开到面板 → 出结果 → 跳到卡 | — | 104 → 1 → 147 ms，命中 1 条 id 正确 | 533 → 1 → 712 ms |

200 档的缩放 p50 与平移 p50 已达 60 fps 量级。**下面那一行「平移 p95 56 ms」是错的，见本文后面的复核**：那次平移用合成事件驱动、视口一秒都没动，页面里还堆着十几张历史画布；改真鼠标 + 干净页面后是 p95 17.8 ms、零帧超标。1,000 档按约定只记录、不套用 200 档目标。三条明确结论：

1. **12 个节点时缩放曾也要 200 ms**，说明当时卡的来源与节点数量无关。
2. **主因是侧栏入口在监听整份 DOM**：`src/client/sidebar-entry.ts` 的 `MutationObserver` 挂在 `document.body` 上，画布每重画一批节点它就被调用一次，而每次都要经 `isVisible` 对祖先链逐个 `getComputedStyle`——那是强制重排。CPU profile 里 5 次缩放共 2179 ms，`isVisible` 自耗 845 ms。改为跳过画布内部变更 + 同轮合并（`setTimeout(0)`，不能用 rAF：页面不可见时 rAF 不跑，入口就永远不挂）后，同一份 profile 里该函数不再出现（总 1461 ms，无单函数超过 50 ms）。
3. **1,000 档剩下的时间主要不在 React**：profile 中 React 侧的 `NodeBody`/`StoryboardBody`/memo 合计约 26 ms，而浏览器 `(program)` 段 346 ms——提交与绘制 1,000 个节点约 6.3 万个元素的成本。已实测 `content-visibility: auto` 对 1,000 档无效（p50 442→420 ms，属噪声），不要再试；真正要解决需让视口外的节点不进入 DOM，而这一档的取舍（框选、连线、撤销是否仍正确）本轮未验证。

### 复核：上一份平移数字是无效的（同日晚）

上一版把「平移 p95 56 ms」当成结论，这个数字**不成立**。两处测量缺陷：

1. **那份平移根本没用真平移。** `panSource()` 用 `dispatchEvent(new PointerEvent(...))` 合成事件打到 `.react-flow__pane`。画布平移由 d3-zoom 驱动，它挂在 `mousedown` 上；合成的 `PointerEvent` 不会派发浏览器兼容的 `mousedown`。实测视口 transform 从头到尾都是 `translate(0px, 0px)`——量到的是一张没动过的画布。而且选择工具下拖背景是**框选**，不是平移，必须先点「拖动画布」工具，这一步原来也缺。
2. **页面里堆了同一批历史画布。** 同一档画布被反复导入，每次新建一份，旧的那份仍在 DOM 里。等到测第 N 次时，一个页面同时挂着十几张 200 节点画布。

修掉这两处后（`scripts/benchmark-canvas-interaction.mjs` 现在会断言视口真的位移过、断言卡片数达标、平移改走 CDP `Input.dispatchMouseEvent` 真鼠标），200 档的平移读数是：

| 指标 | 旧（合成事件 / 脏页面） | 真鼠标，干净页面 |
| --- | --- | --- |
| 平移帧间隔 p50 | 16.7 ms | **16.7 ms** |
| 平移帧间隔 p95 | 56 ms（无效） | **17.8 ms** |
| 超 33 ms 的帧 | 8 / 45 | **0 / 45** |

同一轮按真鼠标重测确认：**200 档平移达 P1 门槛（p95 ≤ 33 ms）**。1,000 档重测为 p50 8.9 / p95 51.1 ms（21 帧超标），仍按约定只记录、不套用 200 档目标——它的瓶颈在 6.3 万元素的提交成本，不是帧循环。

**顺带修掉一个真实的强制重排。** 真平移时 CPU profile 里 `isVisible` 又出现在 `ensure` 链上（108 ms）。原因不是画布：宿主的顶栏有一组装饰性粒子，每次交互都会摘掉一个 `span[class*="particle"]`，旧判据「画布之外有任何节点变更就算相关」把它们全当真，于是每次真平移都排一次 `ensure()`，其中对整棵树做 `getComputedStyle` 就是强制重排。`touchesSidebar` 改成「变更目标或插入/移除的元素必须与当前侧栏根有包含关系；根未解析时一律当真」，`isVisible` 的调用从 288 次降到 **0**。

但要如实说清它在那次测量里的份额：A/B（禁掉挂在 `body` 上的 observer）显示 56 → 18 ms，可这禁掉的不止我们的 observer。修完再看 `long-animation-frame`，长帧的形状是 `blocking 0 ms / styleAndLayout 1–2 ms / 脚本 8 ms`，其余全在 `renderStart` 之后——**是合成与光栅化，不是布局**。所以这一次的收益主要落在「别每帧强制重排」上，而 56 ms 的主要成因是脏页面叠出来的复合层，不是侧栏。两条都保留，但不要把侧栏这条写成了 56 ms 的答案。

同轮修掉的第二个缺陷：**窄画幅下搜索跳转会把卡缩成看不清**。`jumpToNode` 用「视口高 − 顶栏 − 底栏浮层」作为可用高度，而三栏窄画幅里边距合计 74 px、视口仅 332 px，可用高度被压到 1 px，`focusViewport` 的比例一路夹到 `MIN_SCALE`（0.05）——搜到卡、回车，卡变成 16 px 宽、视口位移到画布角落。给可用区设下限（不低于视口一半且不少于 160 px）后，同一场景 k=0.47、卡片宽 151 px 且居中。这条属于「搜索把人送丢」，优先级等同功能缺失。
